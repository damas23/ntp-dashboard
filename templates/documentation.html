Quick start

  1. Check NTP Server Health for synchronization, source, and system offset.
  2. Click a Client Overview card to open a popup window with its full client list. Total Clients shows all addresses; OK, Stale, Warning, and Critical show only that status. These lists refresh automatically and offer address search and sorting. Clicking another card reuses the client popup window.
  3. Client subnet groups start collapsed on every page load. Click a subnet header to show its addresses, then an address to see its packet details.
  4. The expand/collapse switch opens or closes all client groups and details. Manual changes last while the page is open, including automatic refreshes.
  5. Use the search box to filter addresses or statuses. Matching groups remain collapsed until you open them. Use the sort menu to order their clients.
  6. Scroll below the clients to Time History. Live data refreshes about every 5 seconds; history refreshes every 60 seconds.

The theme switch saves your light/dark preference. Information shows project credits; Documentation opens this reusable window.

Understanding server health

Sync state and sync source
Whether chrony is synchronized to an upstream time source, and which reference it is using. A local fallback clock is not proof of synchronization to external time.
Stratum
Distance from a reference clock in the NTP hierarchy. Stratum 1 connects directly to a reference; stratum 2 synchronizes to stratum 1, and so on. A lower stratum alone does not guarantee better accuracy. This server is configured with a stratum-10 local fallback.
System offset
The remaining difference between the system clock and chrony's estimated NTP time. Small values near zero are generally desirable; also check synchronization, source quality, and whether the data is current.
Leap status
Normal means no leap-second adjustment is announced. Insert/Delete indicates an announced leap second; Not synchronised means time synchronization is unavailable.
NTP packets
Chrony's received and dropped packet counters. These are counts, not a packets-per-second rate.

The server's own synchronization and a client's request activity are different measurements. Seeing a client here does not prove that the client's clock is accurate.

Client table and status labels

Each subnet header shows a device count and the most severe status among its matching clients. Summary cards reflect the dashboard's current search filter. Clicking a card opens all clients of that status in a popup window, independent of the dashboard search; the popup has its own search.

NTP / Drop / Cmd
Received NTP requests, dropped NTP requests, and command packets reported for the client. Counters can reset when chrony restarts or client records are removed.
Interval
Estimated request interval in log₂(seconds): 6 means about 64 seconds, 10 about 1,024 seconds. Unknown values are not usable as a polling interval.
Last seen / Stale after
Time since the last NTP request, and the dashboard's inactivity threshold. The threshold is the greater of 300 seconds or three estimated request intervals; unknown intervals use 300 seconds.
  • OK: no reported drops, with a request inside the inactivity threshold.
  • Stale: no reported drops, but the last request exceeds the threshold.
  • Warning: 1–9 dropped requests, or missing/invalid drop or last-seen values.
  • Critical: 10 or more dropped requests.

These are dashboard rules based on request activity, not a measurement of client clock error. Drop counts are cumulative: a warning can remain after an earlier problem has stopped.

Clock offset, frequency drift, and logs

Clock offset: how far apart are the clocks?

An offset estimates a difference in time. For example, 200 µs is 0.2 milliseconds, or 0.0002 seconds. The history chart uses the offset recorded at chrony's tracking updates; it is not the same field as the live System offset card.

Units: 1 second = 1,000 milliseconds (ms) = 1,000,000 microseconds (µs).

Frequency drift: how fast does the clock gain or lose time?

Frequency is measured in parts per million (ppm). One ppm corresponds to one microsecond per second, or 86.4 milliseconds per day. An uncorrected clock with 4 ppm drift would gain or lose about 0.346 seconds per day.

Chrony's frequency estimate describes the clock's rate error without its correction. Positive means naturally fast; negative means naturally slow. Chrony compensates for that error, so a nonzero frequency value can coexist with an offset close to zero.

Chrony normally adjusts the clock rate gradually. It can also step the clock when configured to do so, for example during startup. Look for sustained changes and synchronization loss rather than judging a single sample.

History table and sample range

The history table displays 20 records per page. Use Previous and Next below the table to browse older records. The page indicator shows the current page and record range. Automatic refresh keeps the current page number where possible; changing the sample range returns to page 1. Charts still show the full selected sample range.

Rows show timestamps in both UTC and UTC +7 (WIB), followed by source, leap code, stratum, offset, and frequency (ppm), newest first. The UTC +7 column automatically adds seven hours, including date changes across midnight. Leap code N means normal; ? means unsynchronized.

The selector requests a sample count, not a fixed number of hours. Only available recent entries are shown; the current API caps tracking history at 180 entries, so selecting 400 cannot yet show more than 180. Entries arrive when chrony updates tracking, not on a guaranteed 64-second schedule.

Log files and retention

  • /var/log/chrony/tracking.log — server tracking updates, used by the history charts and table.
  • /var/log/chrony/measurements.log — measurements from upstream sources.
  • /var/log/chrony/statistics.log — per-source statistical estimates.

Logs rotate weekly with four rotated copies retained. The dashboard reads the current files only; archived logs are not included, so the displayed history can shorten after rotation. Data from before logging was enabled is unavailable.

Troubleshooting

No client addresses visible?
Click a subnet header or use Expand all. This compact default keeps Time History close to the client section.
Not synced or stratum 10?
After a restart, allow time for chrony to collect samples. If it persists, an administrator should check upstream reachability and chronyc tracking / chronyc sources -v.
Data refresh failed?
Check the last successful update. Previously displayed values may be stale. An administrator can check systemctl status chrony ticc-dash nginx.
Empty or sparse history?
Wait for tracking updates. Logging may have just started or rotated. An administrator can check the log files and journalctl -u chrony -u ticc-dash.
Documentation opens in a tab?
The browser controls whether the requested popup is a window or tab. The page also works directly at /documentation.
